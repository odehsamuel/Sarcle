# Canonical Observation Format v2 (PoW-OBS-v2)

This specification defines the exact binary format signed by edge devices (e.g. ESP32-CAM) and verified on-chain by the `evidence_registry` Soroban contract.

---

## 1. Binary Layout (115 Bytes Total)

Every observation attestation signature is computed over an immutable, fixed-length 115-byte message payload. No variable-length fields or dynamic encodings (such as protobuf or JSON) are used for the hardware signature to guarantee byte-for-byte reproducibility across embedded C++, Python, and Rust.

| Offset | Field Name | Type | Length | Description |
| :--- | :--- | :--- | :--- | :--- |
| `0..10` | `domain_tag` | ASCII String | 10 bytes | Fixed prefix: `ASCII("PoW-OBS-v2")` |
| `10..42` | `device_id` | Raw Bytes | 32 bytes | Ed25519 public key of the registered edge camera device |
| `42..50` | `job_ref` | `u64` (big-endian) | 8 bytes | Opaque job identifier or escrow reference ID |
| `50..51` | `kind` | `u8` | 1 byte | Observation stage: `0` = Baseline, `1` = Completion, `2` = Followup |
| `51..59` | `counter` | `u64` (big-endian) | 8 bytes | Strictly increasing monotonic sequence counter stored in device NVS |
| `59..67` | `timestamp` | `u64` (big-endian) | 8 bytes | Unix epoch timestamp (seconds) synchronized via NTP |
| `67..83` | `challenge` | Raw Bytes | 16 bytes | Unpredictable nonce issued by `evidence_registry::request_challenge` |
| `83..115` | `image_sha256` | Raw Bytes | 32 bytes | SHA-256 digest computed over the exact captured JPEG byte stream |

---

## 2. Field Specifications

### 2.1 Domain Tag (`0..10`)
* **Value**: Exact 10 ASCII characters: `0x50, 0x6F, 0x57, 0x2D, 0x4F, 0x42, 0x53, 0x2D, 0x76, 0x32` (`"PoW-OBS-v2"`).
* **Purpose**: Prevents cross-protocol signature replay attacks against other Ed25519 signing operations on Stellar accounts.

### 2.2 Device ID (`10..42`)
* The raw 32-byte Ed25519 public key of the capture device.
* Must match an active, unrevoked device registered in `evidence_registry`.

### 2.3 Job Reference (`42..50`)
* Big-endian 64-bit integer (`u64be`).
* Corresponds to the `job_id` within the `work_escrow` contract.

### 2.4 Kind (`50..51`)
* `0x00`: `Baseline` — Captured prior to starting field weeding.
* `0x01`: `Completion` — Captured immediately upon clearing the defined region.
* `0x02`: `Followup` — Captured after the required retention window to measure regrowth.
* Values $\ge 3$ are strictly invalid and rejected by the smart contract.

### 2.5 Counter (`51..59`)
* Big-endian 64-bit integer (`u64be`).
* Edge devices must persist this counter in non-volatile storage (NVS) and increment it before signing each frame.
* Smart contract requires: `counter > LastCounter(device_id)`. Replays or lower counters fail verification.

### 2.6 Timestamp (`59..67`)
* Big-endian 64-bit integer (`u64be`), unix epoch seconds.
* Must satisfy the registry timestamp tolerance:
  $$\text{issued\_at} - \text{tolerance} \le \text{timestamp} \le \text{expires\_at} + \text{tolerance}$$

### 2.7 Challenge (`67..83`)
* 16 unpredictable bytes generated by `evidence_registry::request_challenge`.
* Binds the captured frame to a fresh ledger state and prevents pre-recorded frame injection.

### 2.8 Image SHA-256 (`83..115`)
* Standard SHA-256 cryptographic digest of the complete JPEG file payload as captured from camera DMA memory.

---

## 3. Cryptographic Signature

* **Algorithm**: Ed25519 (Edwards-curve Digital Signature Algorithm over Curve25519, SHA-512).
* **Keypair**: Stellar standard Ed25519 keypair.
* **Verification**: In Soroban, signature verification is performed using:
  ```rust
  env.crypto().ed25519_verify(&device_id, &message_bytes, &signature);
  ```
  where `message_bytes` is the 115-byte reconstituted buffer and `signature` is a 64-byte `BytesN<64>`.
